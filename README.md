# Synapse Curation and Document Processing Setup

This repository contains three Python scripts that provision a simple Synapse environment for testing RecordSet-based metadata curation and document-processing compute tasks.

The scripts create the following workflow:

```text
Synapse Project
│
├── Inputs
│      │
│      └── source documents
│
├── TargetRecordSet
│      │
│      └── RecordSet
│             │
│             └── JSON Schema
│
├── Curation Task
│      │
│      └── targets the RecordSet
│
└── Compute Task
       │
       ├── reads documents from Inputs
       │
       └── sends generated records to the Curation Task
                       │
                       ▼
                    RecordSet
```

## Repository contents

```text
.
├── README.md
├── 01_create_project.py
├── 02_create_curation_task.py
└── 03_create_compute_task.py
```

### `01_create_project_workspace.py`

Creates a new Synapse project and two folders:

```text
<Project Name>
│
├── Inputs
└── TargetRecordSet
```

The script prints the Synapse IDs for:

* the new Project;
* the `Inputs` folder;
* the `TargetRecordSet` folder.

These IDs are used as configuration values in the other scripts.

### `02_create_curation_task.py`

Creates the RecordSet-based curation workflow.

The script:

1. uploads a CSV containing the initial records - it can be empty;
2. creates a `RecordSet` in the `TargetRecordSet` folder;
3. assigns one or more required upsert keys;
4. binds a registered Synapse JSON Schema to the RecordSet;
5. creates a record-based Curation Task associated with the RecordSet; and
6. optionally (recommended) creates a Grid session for that Curation Task, if Grid creation is enabled in the script.

### `03_create_doc_processing_compute_task.py`

Creates a document-processing Compute Task using the Synapse REST API. E.g the task performs ETL operations converting inputs like PDFs, CSVs to the target schema specified in the Curation task above.

The script uses the authenticated Synapse Python client for REST calls, so a separate HTTP authentication implementation is not needed.

The Compute Task:

```text
Inputs folder
     │
     │ source documents
     ▼
Document-processing Compute Task
     │
     │ destinationTaskId
     ▼
Existing Curation Task
     │
     ▼
RecordSet
```

The Compute Task is configured using `RecordSetGenerationExecutionProperties` and points to the existing record-based Curation Task through its `destinationTaskId`.

This script creates and initializes the Compute Task. It does not need to recreate the destination RecordSet or Curation Task.

# Prerequisites

You will need:

* Python 3;
* a Synapse account;
* a Synapse Personal Access Token with permissions sufficient to create and modify the relevant Synapse resources;
* a registered Synapse JSON Schema for the RecordSet;
* an initial CSV for creating the RecordSet; and
* source documents to place in the `Inputs` folder if you intend to run the document-processing Compute Task.

Install the Synapse Python client with the Curator dependencies:

```bash
pip install "synapseclient[curator]"
```

For reproducible environments, consider pinning the version that you have tested:

```text
synapseclient[curator]==<tested-version>
```

in a `requirements.txt`, followed by:

```bash
pip install -r requirements.txt
```

# Authentication

Do not put Synapse credentials directly in these scripts or commit credentials to GitHub.

The recommended setup for these examples is to place your Synapse Personal Access Token in the `SYNAPSE_AUTH_TOKEN` environment variable:

```bash
export SYNAPSE_AUTH_TOKEN="<your-personal-access-token>"
```

The scripts can then authenticate with:

```python
from synapseclient import Synapse

syn = Synapse()
syn.login()
```

Alternatively, you can configure authentication creating a `~/.synapseConfig` file and adding the section

```python
[authentication]

authtoken = your_token_here
```

You can obtain your authentication token by going to Synapse, clicking on your profile icon, and then accessing  Account Settings -> Personal Access Tokens

# Running the workflow

The scripts should be run in order because IDs generated by one step are inputs to subsequent steps.

## Step 1 — Create the Synapse project

Open:

```text
01_create_project.py
```

and configure:

```python
PROJECT_NAME = "My Unique Synapse Project Name"

PROJECT_DESCRIPTION = (
    "Project created for document processing and RecordSet curation."
)
```

Then run:

```bash
python 01_create_project.py
```

The script will print something similar to:

```text
Success
----------------------------------------
Project:                syn12345678
Inputs folder:          syn12345679
TargetRecordSet folder: syn12345680
```

Save these three Synapse IDs.

They will be used as follows:

| Output                    | Used by                                |
| ------------------------- | -------------------------------------- |
| Project ID                | Curation Task and Compute Task scripts |
| Inputs folder ID          | Compute Task script                    |
| TargetRecordSet folder ID | Curation Task script                   |

---

# Step 2 — Create the RecordSet and Curation Task

Open:

```text
02_create_curation_task.py
```

Configure the project and destination folder using the IDs returned by Step 1:

```python
PROJECT_ID = "syn12345678"

PARENT_FOLDER_ID = "syn12345680"
```

Configure the local CSV:

```python
CSV_PATH = "records.csv"
```

Configure the RecordSet:

```python
RECORDSET_NAME = "My RecordSet"

DESCRIPTION = (
    "RecordSet used for document processing and metadata curation."
)
```

Configure the registered Synapse JSON Schema:

```python
SCHEMA_URI = "YOUR_SCHEMA_URI_HERE"
```

## Configure the upsert key

A RecordSet requires at least one upsert key.

For example, if the CSV contains:

```csv
recordId,participantId,diagnosis
record001,P001,AML
record002,P002,ALL
```

configure:

```python
UPSERT_KEYS = ["recordId"]
```

If record identity depends on multiple columns, use a composite key:

```python
UPSERT_KEYS = [
    "participantId",
    "visitId",
]
```

The upsert key should identify the logical record consistently across future updates. Avoid using a row number or temporary CSV index unless it is intended to be a persistent identifier.

## Configure the Curation Task

Configure a data type and instructions:

```python
CURATION_TASK_DATA_TYPE = "clinical_metadata"

CURATION_TASK_INSTRUCTIONS = (
    "Review and complete the metadata records. "
    "Ensure all required fields satisfy the associated JSON Schema."
)
```

The Curation Task will contain:

```text
RecordBasedMetadataTaskProperties
        │
        └── recordSetId
                │
                ▼
             RecordSet
```

Run the script:

```bash
python 02_create_curation_task.py
```

The output should include IDs similar to:

```text
RecordSet ID:       syn12345681
Curation Task ID:   12345
Grid session ID:    67890
```

The exact output depends on whether the script is configured to create a Grid session.

Save the **Curation Task ID**. This is needed by the Compute Task script.

> Important: a Curation Task ID is not a Synapse entity ID. For example, a task ID may be `12345`, while the RecordSet has an entity ID such as `syn12345681`.

Upload the documents you want to process into the project's:

```text
Inputs
```

folder created in Step 1.

The resulting project may look like:

```text
My Synapse Project

├── Inputs
│      ├── report_001.pdf

└── TargetRecordSet
```

The Compute Task will use the Synapse ID of `Inputs` as its source folder.

# Step 4 — Create the document-processing Compute Task

Open:

```text
03_create_compute_task.py
```

Configure the Project ID from Step 1:

```python
PROJECT_ID = "syn12345678"
```

Configure the existing Curation Task ID from Step 2:

```python
DESTINATION_CURATION_TASK_ID = 12345
```

Do **not** use the RecordSet's `syn...` ID here.

Configure the `Inputs` folder ID from Step 1:

```python
SOURCE_DOCUMENT_FOLDER_ID = "syn12345679"
```

Configure a distinct data type for the Compute Task:

```python
COMPUTE_TASK_DATA_TYPE = "clinical_document_processing"
```

The Compute Task data type should be distinct from the data type used by the record-based Curation Task.

Configure the human-readable task description:

```python
COMPUTE_TASK_INSTRUCTIONS = (
    "Extract structured metadata from the source documents "
    "and populate the associated RecordSet."
)
```

Then configure the document-processing instructions:

```python
DOCUMENT_PROCESSING_INSTRUCTIONS = """
Extract the metadata described by the JSON Schema associated with
the destination RecordSet.

Produce one row per logical record.

Use the source documents to populate all fields that can be
determined from the documents.

Do not invent values that are not supported by the source material.
""".strip()
```

Run:

```bash
python 03_create_compute_task.py
```

The script will:

```text
Existing Curation Task
        │
        └── validate destination RecordSet

Inputs folder
        │
        ▼
Create Compute Task
        │
        ├── folderId = Inputs
        ├── instructions = extraction instructions
        └── destinationTaskId = existing Curation Task
        │
        ▼
Initialize execution details
```

Successful output should include something similar to:

```text
Success
-------------------------------------------
Project:               syn12345678
Destination Task:      12345
Destination RecordSet: syn12345681
Source Folder:         syn12345679
Compute Task ID:       54321
Compute Task state:    NOT_STARTED
```

Save the Compute Task ID if you plan to execute or inspect the task later.

# Configuration handoff between scripts

The key identifiers move through the workflow as follows:

```text
01_create_project.py
│
├── project.id
│       │
│       ├────────────► 02_create_curation_task.py
│       └────────────► 03_create_compute_task.py
│
├── inputs_folder.id
│       │
│       └────────────► 03_create_compute_task.py
│
└── target_recordset_folder.id
        │
        └────────────► 02_create_curation_task.py


02_create_curation_task.py
│
├── record_set.id
│       │
│       └── referenced by the Curation Task
│
└── curation_task.task_id
        │
        └────────────► 03_create_compute_task.py
```

In configuration-variable terms:

| Generated value              | Destination variable           |
| ---------------------------- | ------------------------------ |
| `project.id`                 | `PROJECT_ID`                   |
| `inputs_folder.id`           | `SOURCE_DOCUMENT_FOLDER_ID`    |
| `target_recordset_folder.id` | `PARENT_FOLDER_ID`             |
| `curation_task.task_id`      | `DESTINATION_CURATION_TASK_ID` |

# Python client vs. REST API

The repository intentionally uses both interfaces.

The project and RecordSet/Curation Task scripts primarily use the stable Synapse Python client.

The Compute Task script uses:

```python
syn.restGET(...)
syn.restPOST(...)
syn.restPUT(...)
```

for the Curation/Compute REST endpoints.

This allows the repository to stay on a stable Synapse Python client while still accessing Compute Task functionality that may not yet be represented by equivalent high-level client objects in the installed stable release.

Authentication is still handled by the same logged-in `Synapse` client.

For example:

```python
syn = Synapse()
syn.login()

compute_task = syn.restPOST(
    "/curation/task",
    body=json.dumps(payload),
)
```

# Grid authorization

Some stable Synapse Python client releases do not expose:

```python
AuthorizationMode
```

or:

```python
suggested_authorization_mode
```

on `RecordBasedMetadataTaskProperties`.

If you encounter:

```text
ImportError: cannot import name 'AuthorizationMode'
```

do not import that class in a script intended to remain compatible with your installed stable client.

If shared Grid authorization such as:

```text
SOURCE_BENEFACTOR
```

is required, configure it through the corresponding REST API rather than depending on a client API that is not available in the stable version you are using.

`SOURCE_BENEFACTOR` authorization and actually granting users `EDIT` access are separate concerns. Users still need appropriate permissions on the relevant Synapse source or its permission benefactor.

# Re-running scripts

These scripts provision Synapse resources, so re-running them should be done intentionally.

### Project creation

`01_create_project.py` is intended to provision a new project. Use a different project name if you intend to create a separate environment.

### Curation Task creation

If you already have a RecordSet and Curation Task, avoid rerunning the entire provisioning workflow solely to make a small change to the existing task.

For updates, it is generally safer to retrieve the existing task using its task ID and modify that task explicitly.

### Compute Task creation

Running `03_create_compute_task.py` again may create another Compute Task unless the script explicitly implements lookup/update behavior.

If you intend to update an existing Compute Task instead of creating another one, retrieve the existing task first and perform an explicit update.

# Troubleshooting

### `400 Client Error: The upsertKey is required and must not be empty`

Configure at least one valid column:

```python
UPSERT_KEYS = ["recordId"]
```

The column must exist in the source CSV.

### `ImportError: cannot import name 'AuthorizationMode'`

Your installed stable Synapse Python client does not expose that class.

Remove the import:

```python
from synapseclient.models import AuthorizationMode
```

and avoid using the enum in stable-client code.

### Curation Task ID vs. RecordSet ID

The Compute Task requires:

```python
"destinationTaskId": DESTINATION_CURATION_TASK_ID
```

For example:

```python
DESTINATION_CURATION_TASK_ID = 12345
```

It does **not** take:

```python
DESTINATION_CURATION_TASK_ID = "syn12345681"
```

The latter is the RecordSet entity ID.

### Compute Task points to the wrong project

Verify that:

```python
PROJECT_ID
```

is the project containing the destination Curation Task.

The Compute Task script validates this before creating the new task.

### Authentication fails

Confirm that your token is available:

```bash
echo $SYNAPSE_AUTH_TOKEN
```

Do not print the token itself in shared logs or screenshots.

You can also test authentication independently:

```python
from synapseclient import Synapse

syn = Synapse()
syn.login()

print(syn.getUserProfile()["userName"])
```

# Example end-to-end workflow

After configuring authentication:

```bash
export SYNAPSE_AUTH_TOKEN="<your-token>"
```

create the Synapse environment:

```bash
python 01_create_project.py
```

Copy the generated Project and folder IDs into `02_create_curation_task.py`, then run:

```bash
python 02_create_curation_task.py
```

Copy the resulting Curation Task ID into `03_create_compute_task.py`, configure its source folder using the `Inputs` folder ID, then run:

```bash
python 03_create_compute_task.py
```

At that point the Synapse environment should contain:

```text
Project
│
├── Inputs
│      └── source documents
│
├── TargetRecordSet
│      └── RecordSet
│             └── JSON Schema
│
├── record-based Curation Task
│      └── RecordSet
│
└── document-processing Compute Task
       ├── source: Inputs
       └── destination: Curation Task
```

The environment is then ready for subsequent execution and testing of the document-processing workflow.
